# Security Boundaries

OpenClaw is an orchestration and agent layer, not the final authorization boundary. Support Core and its trusted integration adapters own identity resolution, ownership checks, authorization, and policy enforcement.

Markdown knowledge is shared reference data, not identity, ownership, approval or executable policy. The operator selects a reviewed directory; OpenClaw may search and read opaque versioned article references through signed-ticket Core routes. It cannot supply a root or arbitrary path. The adapter ignores symlinks/junctions, bounds reads and never executes code or follows document links. Knowledge tools inherit ticket checks and suppress results after takeover. Documents must contain no credentials or private customer records; they can appear in model transcripts and customer answers even when excluded from Git. Prompt injection is treated as data and cannot create a new Core capability or mutation approval.

Support Core must never trust customer IDs, claims of service ownership, Pterodactyl server UUID ownership, or authorization decisions generated by a model. Every customer-specific operation must follow:

```text
Discord actor
  -> resolve linked WHMCS customer
  -> resolve owned WHMCS services
  -> resolve corresponding Pterodactyl resource
  -> authorize operation
  -> perform operation
```

A model-provided identifier is only a selector within resources already proven to belong to the resolved customer. It is not ownership evidence. Failures must fail closed, including ambiguous mappings and unavailable upstreams.

WHMCS and Pterodactyl privileged credentials remain inside their adapters. They must never be exposed to the model, Discord, shared contracts, error details, or logs. The agent must not receive arbitrary HTTP, arbitrary provider API, refund, termination, deletion, or destructive restore capabilities.

Correlation IDs are operational metadata, not authentication. The prototype transport uses sixty-second HMAC ticket capsules issued by a trusted bot context, with actor/guild/channel binding and an authoritative ticket-state check per operation. The agent has neither a signing key nor authority to choose a customer. Core rechecks ticket state before releasing awaited customer data; the final bot send still requires a serialized state check against takeover/close.

Unknown sessions get no tools. Plain identity headers, session naming and model claims are not alternatives to the signed context. Capsules are bearer credentials and contain identity in cleartext encoding; keep them out of model text, logs and URLs. Production requires a protected TLS network, rotated random key, verified host/session binding and real bot state/send adapters. Read-only replay within sixty seconds is possible; this context does not authorize provider mutations beyond the separately bounded restart policy.

Core discards raw arbitrary port-error causes as well as provider error bodies. Neither generic provider HTTP nor full customer/service/container records cross the tool boundary. Handoff text is bounded, split for Discord, has mentions disabled and is explicitly agent-reported/unverified.

Optional audit output is a separate staff-only Discord channel. Its recorder projects only a fixed operation, outcome and random correlation ID, bounds pending sends, disables mentions, rechecks cached channel privacy and never blocks or changes customer authorization. It is operational evidence, not a source of identity or ownership.

The unchanged-baseline launcher admits only an explicit test channel. It decorates the shared model's lazy mutation execution and serializes it against AI delivery; any guarded legacy mutation revokes all AI admission. Single-process overlays are not durable storage: restart disables AI and uncertain sends cannot be retried blindly. External writers and additional bot processes are outside this prototype's guarantee. OpenClaw's native turn route uses Gateway auth plus Core capsule verification, bounds sessions to a verified scope, and passes capsules only as runtime `toolBindings`. Its fixed tool allowlists contain no exec, arbitrary filesystem, direct provider administration or arbitrary messaging tool. Server-file/startup reads remain scoped by Core ownership; state changes use Core's bounded restart or separately approved mutation workflow.

The bounded `restart_my_server` operation is the first low-risk provider write. It still requires Core ownership and state checks, a per-actor/service cooldown and post-operation verification; ambiguous or uncertain results fail closed. Other provider writes require a Core-issued operation approval bound to the signed ticket scope, current revision, operation digest and expiry. A model cannot approve its own proposal. Improvement data follows a reviewed eval pipeline; production permissions and tool schemas are never learned from unreviewed conversation.
